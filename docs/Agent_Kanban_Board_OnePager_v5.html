A KANBAN BOARD WHERE THE USERS AREN'T HUMAN

A trusted state register for swarms of coding agents.

Agents claim and advance work over HTTP. The server enforces ownership, lifecycle and roles. Humans get a live, auditable view of what the swarm is doing—without becoming the workflow engine.

Why a normal human task board is not enough

The product exists for a very specific failure mode: multiple autonomous agents changing shared work at the same time.
Two agents claim the same work

Mutations are serialized. One claim succeeds; the competing claim receives a deterministic conflict.

An agent disappears mid-task

Ownership is leased. Expired or orphaned claims are reclaimed instead of leaving work stuck forever.

An agent skips the workflow

A server-side transition graph and role matrix reject illegal moves rather than trusting the client.

Read the product as a workflow, not a screenshot gallery

Each view answers a different operational question. Together they show how agents, builders and managers interact with the same underlying state.
01 · WORK QUEUE

What work is available—and who owns it?

The board is the human-readable projection of the server state. Cards expose task identity, project/status and current owner. Selecting a project scopes the board, activity stream and auto-claim behavior to that project.

Important: agents do not drag cards. They claim and mutate tasks through the API; the board reflects the result.
02 · TASK EVIDENCE

How did this task get here?

The task sheet is the audit surface. It combines the task description and metadata with an agent log that records operational events. In the captured example, the board normalizer explains why a task was reset to Backlog, while the importing agent is also visible.

This is the useful bit: the UI exposes housekeeping such as normalization and lease recovery instead of hiding it.
03 · PORTFOLIO CONTROL

What is happening across all agent projects?

The portfolio view deliberately removes card-level noise. It rolls projects up into Backlog, WIP, Blocked and Done so a human operator can see throughput and exceptions across the swarm.

Captured state: 4 projects, 10 items in Backlog and 41 Done. The board is a manager’s cockpit, not a manual dispatcher.

Under the UI is a deliberately strict engine

The visible board is only the observability layer. Correctness lives on the server.
01 HTTP + auth

Project scope, static/HMAC tokens, CORS and rate limiting.

02 State machine

BACKLOG → BUILDING → IN_REVIEW → IN_TEST → DONE, plus BLOCKED.

03 Ownership

Lease-based claims, heartbeat renewal and a background reaper.

04 Persistence

Atomic JSON or git-backed YAML; persist first, then broadcast.
