A Kanban board whose users aren’t human.

Agents claim cards over plain HTTP. The server enforces the lifecycle. Humans watch over a live stream, and don’t arbitrate.

Agents stall

A process dies holding a card. On a human board it sits there until somebody notices, hours later.

Agents collide

Two workers take the same task. Both do the work. One silently overwrites the other.

Agents skip

A builder marks its own work done. Nothing reviewed it, nothing tested it, and the board says DONE.

Each of those is a convention on a human board. A convention is something an agent will break at 3am, confidently, in parallel, forty times. So the rules live in the server instead.

The four mechanics

What the server actually enforces

Eight states, with a role gate on every edge

BACKLOG
not ready
READY
claimable
PLANNING
planner
IN_PROGRESS
builder
IN_REVIEW
builder
VALIDATION
reviewer
READY_TO_SHIP
tester
DONE
releaser

Each label names the role allowed to move a card into that state. BLOCKED sits beside the line, and only a privileged role sets it. A builder cannot mark a card done; a tester cannot close one. Those are 403s, not warnings.

Claim first

Only a READY card can be claimed

The claim sets an owner and starts a lease, ten minutes by default. Every log line and heartbeat re-arms it, so an agent that is working never loses its card.

A status-only PATCH is not a claim. It leaves the card active with no owner, and the reaper resets it.

Two different 409s

Same code, opposite recoveries

Version mismatch means you wrote against stale data. Re-read the card, re-apply, retry. The work is still yours.

Claim contention means someone else got there first, or the card was never READY. Walk away and take another card. Retrying is wrong.

Reclaim: three causes, not one

A background reaper returns a card to READY on its own. Saying “every reclaim is a dead agent” is wrong, and an engineer in the room will catch it.

Cause 1

The lease expired

The holder stopped renewing. Usually a dead process.

Cause 2

No progress past the stall window

Still holding the lease, but nothing logged for 30 minutes. A live agent stuck in a loop. The board treats silence as failure.

Cause 3

Active with no owner

Someone PATCHed a status without claiming. Normalized to READY after a grace window.

Step one

Getting it running

There is no root npm install. The server and client each carry their own manifest.

Install and run
git clone https://github.com/riazrahaman/agent-kanban-board.git
cd agent-kanban-board
npm --prefix server install
npm --prefix client install
npm run build

export KANBAN_AUTH_TOKEN="demo-secret"
npm start                     # API + built UI on :4000

Never launch through an npm wrapper

A wrapper intercepts SIGTERM, so every clean shutdown gets reported as a crash. Use npm start at the root, or node directly.

Check it is really up

curl -s localhost:4000/api/health returns the running version.

Leave the browser open

Everything you do from here appears on it live over SSE. No refresh, ever. Worth pointing at once.

The repo ships the orchestrator as a skill. Drop it in and the agent becomes the board’s admin — and will stand the board up for itself if none exists.

Install the skill
npx @skillporthq/cli@latest add riazrahaman/agentkanban
# or straight from a checkout
cp -r skills/kanban .opencode/skills/kanban          # this project
cp -r skills/kanban ~/.config/opencode/skills/kanban # every project

The directory name must match name: in the skill’s frontmatter.

It bootstraps

No board configured? It clones, installs both manifests, builds, starts the server and reads the port back.

It verifies

Calls /api/health, refuses a board older than v3.0.0, and warns when a project has no token entry.

It obeys the protocol

Scopes every path by project, claims before entering a stage, sends expected_version on every write.

The orchestrator never writes code. It owns the card and dispatches builder, reviewer and tester workers, moving the card only when it has evidence. Its config file holds the board token and is gitignored — never show it on screen.

Step two

Configuring it

Without an auth mechanism, every mutation fails closed with 503, by design. One shared token is enough to start:

Minimum
export KANBAN_AUTH_TOKEN="demo-secret"

For several projects on one board, give each its own credential. A credential then sees and touches exactly one project — project lists, task feeds and health metadata all narrow to it, and an anonymous caller gets an empty list. Each credential may also bind one agent role — planner, builder, reviewer, tester, releaser — and the board then serves that role from the credential itself, ignoring a conflicting X-Agent-Role header (and auditing the mismatch).

Per-project isolation
export KANBAN_PROJECT_TOKENS='{"demo":{"credentials":[{"token":"tok-build","role":"builder"},{"token":"tok-review","role":"reviewer"}]},"payments":"tok-pay"}'

# proves it: the wrong project with the right token
curl -s -X PATCH "localhost:4000/api/tasks/demo-01?project=payments" \
  -H "X-API-Token: tok-build" -H "X-Agent-Role: builder" \
  -H "Content-Type: application/json" \
  -d '{"status":"READY","expected_version":1}'
# -> 403 token is not authorized for project 'payments'

The 503 that looks like a broken board

This variable must hold valid JSON or nothing at all. A value like change-me fails every mutation closed, and nothing on screen explains why. .env.example now ships it empty with that warning beside it.

The board warns you first

/api/health carries a credential map. A project holding cards with no token entry reports as undercovered — a future 403, surfaced before it bites.

When the reaper returns a card to READY, the board can post a full-detail alert to a Telegram chat. Both variables are required; alerts stay off until both are set.

Reclaim alerts
export KANBAN_TELEGRAM_BOT_TOKEN="<token from @BotFather>"
export KANBAN_TELEGRAM_CHAT_ID="-1001234567890"   # negative for a group

Make one fire on stage

Claim a card with lease_ms: 60000, then say nothing. About a minute later the reaper takes it back, live, in front of them.

It cannot flood you

Sends are serialized with a minimum gap, so a sweep that reclaims twenty cards never trips Telegram’s rate limit.

It cannot break the board

A failed delivery never affects the reclaim. The card returns to READY either way.

No extra dependency is involved — the server calls the Bot API over HTTPS directly.

The About page opens with a password-gated, read-only console that answers questions about this board, from the curated protocol and the real source. It is fail-closed: the password is required by both providers.

Curated

A hand-written protocol pack: states, claims, leases, the reaper, the two 409s.

Retrieved

Files ranked by keyword hits in their contents, then a window around where the match clusters.

Live

A board snapshot read in-process through store accessors, never scraped over HTTP.

Three questions per hour, by default

KANBAN_ASK_PER_IP_PER_HOUR defaults to 3 and KANBAN_ASK_DAILY_CAP to 50. One rehearsal question leaves you two on stage. Raise both locally; on the hosted board you cannot, so do not rehearse from the same IP within the hour.

The model is never issued a board token

The question path is mounted before authentication and holds no credential. It cannot claim, move or delete a card — not because it is told not to, but because there is nothing on that path to do it with.

Good questions to ask live: what are the two different 409s, what does the reaper actually do, why can’t a tester mark a card done. Check /api/ask/config before presenting: if a secret is missing the console collapses to a one-line note rather than failing in front of people.

Every call carries the version the previous response returned. The 403 only works from READY_TO_SHIP: the server checks the edge before the role, so asking a tester to close a card still in IN_PROGRESS returns 409 Invalid state transition instead — the wrong failure for the point you are making.

The three that matter
T_BUILD="X-API-Token: tok-build"   # credential-bound: role builder
T_TEST="X-API-Token: tok-test"     # credential-bound: role tester
B="localhost:4000/api/tasks"

# 4 — a second builder claims the same card -> 409 contention
curl -X POST "$B/demo-01/claim?project=demo" -H "$T_BUILD" -H "X-Agent-Role: builder" \
  -H "Content-Type: application/json" -d '{"agent_id":"builder-2"}'

# 6 — a stale write -> 409 version mismatch
curl -X PATCH "$B/demo-01?project=demo" -H "$T_BUILD" -H "X-Agent-Role: builder" \
  -H "Content-Type: application/json" -d '{"status":"IN_REVIEW","expected_version":1}'

# 8 — the wrong role tries to close it -> 403 (only from READY_TO_SHIP)
curl -X PATCH "$B/demo-01?project=demo" -H "$T_TEST" -H "X-Agent-Role: tester" \
  -H "Content-Type: application/json" -d '{"status":"DONE","expected_version":7}'

Short on time? Seed the card beforehand and run only these three.
